# Comparing skill revisions

Use this maintenance procedure only when evaluating skill changes. Review explanatory quality manually; no local comment checker is required.

## Hold conditions fixed

Choose Java files covering compact definitions, shared fields, defaults, recovery, concurrency, ownership/reflection, and interacting design decisions. Include a routine library wrapper, a handwritten override, Lombok-backed fields, record components, and JUnit/JMH entry points. Save starting contents, repository revision, AGENTS.md, skill versions, and prompts outside the active checkout. Run both versions from fresh copies of those files with other instructions held constant.

When delegation is available and authorized, use fresh agent contexts with the same model settings. Give an ordinary task and checkout path; let repository instructions discover the skill. Keep expected answers, earlier outputs, and rule reminders out of prompts. Record any setting or instruction difference. Compare new files separately from fixed-file regressions; use unfamiliar files to assess transfer beyond examples used to revise the skill.

## Compare raw results

Preserve original diffs and validation results before any corrections. Agent self-reports do not establish that review passed. Check that each production overview shares one Javadoc with the primary type's contract and states its responsibility before background. Read the whole file for progression from purpose to design, decisions to preserve, useful examples, and distribution of detail. Then inspect:

- Incorrect or unsupported claims, especially ownership and exceptions.
- Missing required coverage or calling rules.
- Repeated facts without additional information.
- Expanded compact definitions or ungrouped shared rules.
- Unrelated facts in design paragraphs, or local comments translating expressions.
- Javadoc attached after annotations, broken inline tags, or inherited text counted as a local explanation.
- Expanded generated accessors, unsupported generated-file exemptions, or record components left undocumented.

Record representative passages and their evidence; group small presentation issues. Counts can locate padding but do not measure quality. A trial leaving fields untouched cannot validate field rules; add a separate type-focused task when needed.

Report code verification separately from comment review. Validate affected Javadoc and follow repository-required checks; retain unresolved findings and label subsequent corrections separately. Improvement on sampled files establishes evidence for those files, not a universal guarantee.
